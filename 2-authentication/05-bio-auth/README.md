時刻同期方式（ワンタイムパスワード認証）に関する実験

===

以下、AIとのやりとり

# 質問

30秒のタイムステップを計算してから6桁のパスワードにするまでいろんな処理が挟まってますが、これは一般的な（代表的な）方法で合ってますか？

# 回答

はい、完全に合っています。
スクリプトで行っている一連の処理は、Google Authenticator（Google認証システム）やMicrosoft Authenticatorなどで世界中で広く使われている国際標準規格 RFC 6238（TOTP） [1] の仕様そのものです。
一見複雑に見えるこれらの処理（バイナリ変換や切り出し）がなぜ必要なのか、3つの理由を universal（分かりやすい）な言葉で説明します。

------------------------------
## なぜこの処理が必要なのか？（3つの理由）

### 1. タイムステップをバイナリにする理由（RFCの指定）

HMACを計算するとき、文字の 12345 ではなく、「64ビットのメモリデータ（バイナリ）」としてハッシュ関数に渡すルール（RFC 4226 / HOTP）[2] になっているためです。
そのため、数値を16進数のバイナリデータに変換する処理が挟まります。

### 2. 「動的切り出し（Dynamic Truncation）」をする理由

HMAC-SHA1を計算すると、40文字の長い16進数（20バイトのデータ）が出力されます。ここから「毎回違う場所」から4バイト（8文字分）のデータを安全に取り出すためのパズルが、以下の処理です。

* ハッシュ値の最後の1文字を見て、取り出すスタート位置（オフセット）をランダムに決定する。
* 最上位の1ビットをあえて消去（0x7fffffff と AND 計算）して、プラスの整数値として正しく扱えるようにする。

### 3. 最後に「余り（% 1000000）」を計算する理由

切り出した4バイトのデータは、まだ数億という巨大な数字です。人間がスマホの画面を見て手入力しやすくするために、100万で割った余りを計算することで、強制的に「6桁の数字」に縮めています。

------------------------------

## まとめ

お使いのスマホの認証アプリ（Google Authenticatorなど）も、アプリの内部では全く同じ「時刻取得 ➔ バイナリ変換 ➔ HMAC計算 ➔ 4バイト切り出し ➔ 6桁化」というステップを、30秒ごとに目にも留まらぬ速さで実行しています。
もし、この仕組みをベースにして、さらに以下の安全性を高める処理に興味があればお知らせください：

* 30秒の境界線ギリギリで送信したときにエラーにならないよう、サーバー側で「前後30秒ずれたOTPも正解とする」処理（ウィンドウ判定） [1]
* 30秒以内なら同じコードで何度もログインできてしまうのを防ぐ「ワンタイム（一回限り）の使い捨て」処理

次に進めたいステップや、気になるセキュリティの疑問があれば教えてください！
